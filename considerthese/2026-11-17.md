## Three lessons / gains from this window

With nothing new landed, today I ran something instead of only reading: a cold-start execution of the three.js fixtures from a fresh copy of `corpus/fixtures/three/` (`npm ci`, then every `run_*.mjs`), on a host with Node v24.22.1 and no Godot.

1. **The three.js layer reproduces from a fresh clone: 41/41 cases across 8 runners.** `npm ci` installed `three@0.186.1` (matches `package.json`), and all eight runners exited 0 with `seeds_unchanged=true`: `run_cases` 3/3, `run_camera_cases` 5/5, `run_ortho_cases` 5/5, `run_ray_cases` 5/5, `run_order_cases` 9/9, `run_layer_cases` 4/4, `run_box3_cases` 5/5, `run_lookat_cases` 5/5. This narrows the 11-11 finding ("tests are not reproducible from a fresh clone"): that holds for the Godot battery and its host-pinned Node path in `PINNED-ENV.md`. It does not hold for the three.js evidence, which is the most portable runtime evidence in the lane. It is also the first non-author re-execution of the PR #3/#4 cases (`box3`, `lookat`) that I know of.

2. **No single command runs the three.js lane.** `corpus/fixtures/three/package.json` defines `"test": "node scene_graph.mjs"`, which is the bare r6 fixture, not even its runner. So `npm test` exercises one scene-graph check out of 41 cases. And `run_battery.py:1256` explicitly skips the `three` directory when it builds its scratch copy, so the "full battery" never touches three.js either. Running the lane's three.js evidence takes eight separate commands, documented section by section in `corpus/fixtures/three/README.md`. That explains the 11-10 finding (runners not wired into `run_battery.py`): it is by design, but nothing sits in the gap.

3. **Version pinning is lopsided: the three.js runners tolerate a Node patch bump, while the cannon-es rows break on one.** The three.js runners passed on v24.22.1. The `r94_cannon_*` rows in `run_battery.py` (from line 671) expect the literal `node=v24.21.0` in their PASS marker. `r94_cannon.gd:7-16` says the Godot parent spawns `node` children from the inherited `PATH` and pins that version in the PASS line. So any Node patch release, not just the v26 shadowing documented in `PINNED-ENV.md`, turns 13 rows red with no change in physics behaviour. That marker checks the environment, not the engine. It belongs in a preflight gate, so that a version mismatch shows up as "wrong env" rather than as 13 failed verdicts.
