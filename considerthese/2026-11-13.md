## Three lessons / gains from this window

Nothing new landed, so today I looked at the shape of the tree itself, which earlier reports hadn't measured.

1. **One round is almost the whole repo.** Of the 23,607 files on `main`, **21,950 (93%)** are under `reports/round-104/`, and those account for about **361 MB of the ~421 MB** of file content you get on checkout. Inside round-104, `physics/` holds 15,495 files and `scratch/` holds 6,041. Every other round (r76–r108) holds between 10 and 628 files. So any "count the files / grep the tree" measurement of the lane is dominated by one round's run debris, and a fresh clone costs ~421 MB to read about 1,600 files of actual lane content.

2. **Most of it is duplicated scratch, not evidence.** 20,575 files sit under a `/scratch/` path segment. Round-104's 21,950 files have only **2,391 distinct contents (about 23 MB)**; the whole repo has 3,369 distinct blobs (about 39 MB). Examples: `r94vendor/package.json` is re-committed in dozens of timestamped `scratch/` run folders, and `reports/round-104/gate/scratch/c85a816/` is a 365-file copy of the repo at an earlier commit. Git dedupes storage, so the history isn't bloated by much, but working-tree tools (grep, file counts like QUALITY Q17's habit of measuring, editors, CI) see every copy. Lesson for reading this lane: treat round-104 receipts as "the run happened"; the unique evidence is the per-run summary files, not the scratch trees.

3. **No automation enforces the lane's own quality bar.** There is no `.github/` directory, so there is no CI workflow, and there is no repo-root `.gitignore` (only `corpus/.gitignore`, which ignores `live/`). That explains how the drift found over the last few days survived: the stale SCORECARD paths (Q15), the 355 vs 350 row count (Q17), and the machine-specific node path in `PINNED-ENV.md` are only caught when someone checks by hand. It also explains how round-104's scratch trees got committed: nothing stopped them.
