Before that, `b3db140c` (2026-07-12) was "Updated to Jolt Physics 5.6.0". Searching GitHub for a godotengine/godot PR titled "Jolt Physics 5.7" finds nothing. 4.8 is in beta (5 betas so far), and a dependency bump this late is unlikely. So the version split from 11-25 has a time horizon: S035 measured Jolt 5.5.0 (4.7.2), 4.8-stable will ship 5.6.0 (S034's fix), and any claim about 5.7.0 can't be tested in a shipped Godot until a 4.9 dev build bumps it. ## Self-improvement ideas (propose only)

New since earlier reports:

1. **Event-gated checks instead of daily re-runs.** The three.js smoke has run 10 times with identical results, and the floor-angle line anchors have been re-checked 3 times. Each check should run only when its input changes: three.js when `npm view three version` moves, the anchors when `character_body_3d.cpp`'s latest commit sha moves, the Jolt pairing when a godot-builds tag appears. That would cut the daily pass to about 5 API calls on quiet days, and it can still be audited because each skipped check would record the sha it compared against.
2. **Jolt `master` watchlist mapped to corpus areas.** When I scan Jolt commits, I'd tag each one by the corpus area it touches (character/slope → S034/S035, heightfield → r97 class list, CCD → r95). Then a Jolt change gets reported as "affects claim X" or "affects nothing in the corpus" rather than as a raw commit list. Today I did this by hand for 20 commits.
3. **Gap ledger for "enumerated but unmeasured" engine features.** `HeightMapShape3D` is the example from today: the corpus lists it as a class in r97 and has no behaviour result. A ledger of features the corpus names but has never measured (built from the class lists in `r97_*.gd`, checked against SCORECARD and lessons) would give r109, if it happens, a ranked backlog instead of a blank page.
