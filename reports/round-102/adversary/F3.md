## 1. The archival argument

A receipt digest is a **snapshot field**. Its correctness criterion is *"equals the artifact as it existed at the moment of the run"*, not *"equals the current tree"*. Under that criterion the r22 lesson's digest is **correct**, and it is the only criterion under which any receipt digest can be correct — a digest that tracked the current tree would be false the moment the tree next changed.

Evidence that the cited digest *is* the r22 artifact, not a typo or a fabricated number:

```
$ git show 8b21cae:corpus/fixtures/run_battery.py | sha256sum
a065a56db193228d2c5f3d0760c02972aee69d59c5c86480d7f9cf444a582570  -
$ git show -s --format='%h %ad %s' --date=iso 8b21cae
8b21cae 2026-10-13 02:38:13 -0300 game-dev-3d r22: verify Unreal-style static descriptor
```

`8b21cae` is the commit that **introduced the lesson itself** (`git show --stat 8b21cae` lists `corpus/lessons/r22-unreal-review.md` among its 6 files). The lesson's own digest therefore hashes to the tree state *in the same commit that wrote it*. This is a perfect archival match, not drift.

The cited digest is also the r21 blob and the r22 record blob (the digest was unchanged r21→r22):

```
$ for c in 490e710d 8b21cae 7804a69; do printf '%s ' "$c"; git show "$c:corpus/fixtures/run_battery.py" | sha256sum | cut -c1-16; done
490e710d a065a56db193228d
8b21cae a065a56db193228d
7804a69 a065a56db193228d
```

And it matches the lesson's *own* case count — the r22 blob contains exactly 29 cases, which is the "29/29" the lesson reports:

```

$ python3 -c "import ast; ... CASES ..."      # current tree

```

So the number is not merely "real somewhere in history" — it is **internally consistent with the very receipt it annotates** (29/29). A stale number would be one that never matched anything; this one matched exactly and still does, at its named round.

## 2. The digest *is* re-derivable — the routed framing's "unreproducible" overstates

The routed wording (via `reports/round-102/before/F3-sha-drift.md:103`) says the digest is "**not reproducible from the tree**". True for the *worktree*, false for the *repository*. I recovered it from history alone, without being told the commit, by walking all 78 blob revisions of the path:

```
$ while read c; do h=$(git cat-file blob "$c:corpus/fixtures/run_battery.py" | sha256sum | cut -d' ' -f1); \
    [ "$h" = "a065a56d…" ] && echo "FOUND in history: $c"; \
  done < <(git log --format='%H' -- corpus/fixtures/run_battery.py)
FOUND in history: 490e710dbe9b0ccd2096716d2ad675771a840a12
```

The blob is reachable from `origin/main`, so **every clone can verify the citation**:

```
$ git merge-base --is-ancestor 8b21cae origin/main && echo REACHABLE
REACHABLE: 8b21cae is an ancestor of origin/main
$ git cat-file -e 8b21cae:corpus/fixtures/run_battery.py && echo "object present in a clone that has main"
object present in a clone that has main
```

The genuine friction is narrower than "unreproducible": the lesson **does not name the commit**, so a reader must do a 78-commit walk to locate the blob. That is a *pointer-completeness* defect, and it is repaired by *adding the commit pointer*, not by replacing the digest.

The r22 blob is **not** a prefix of the current file, so the historical content cannot be reconstructed from the current tree — git is the only source, which is exactly why the fix must cite a commit rather than "just re-derive it":

```
$ wc -l /tmp/r22-blob.py corpus/fixtures/run_battery.py

$ head -n 591 corpus/fixtures/run_battery.py | diff -q - /tmp/r22-blob.py  →  NOT A PREFIX
```

**Corollary — silent renumbering is the wrong repair.** Replacing `a065a56d…` with the current `f456bd00…` would (a) destroy the r22 archival record, (b) substitute a number true only today, and (c) guarantee a fresh "F3" every round, since 78 commits have produced 78 distinct digests.
